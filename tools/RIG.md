# Испытательный стенд

Стенд перенесён из проекта ESPidi-rebuilt (github.com/zemuro/ESPidi-rebuilt, каталог `tools/`), где он
нашёл 23 дефекта прошивки ESPidi и подтвердил их исправление. Для RED SEA общую часть можно брать как есть,
а обвязку прошивки и тесты нужно написать заново — ниже сказано, что именно.

## Как устроено

```
 ПК ── USB-MIDI кабель (DIN) ── переходники TRS→DIN ──▶ MIDI IN  ┐
   ◀──────────────────────────────────────────────────── MIDI OUT ┤ устройство
 ПК ── USB-C (консоль тестовой прошивки + прошивка) ───────────── ┘
```

- **MIDI.** ПК играет ноты, CC, Clock и Start/Stop во вход устройства и записывает всё, что выходит
  с MIDI OUT, с отметками времени.
- **USB-консоль.** Тестовая сборка прошивки принимает команды и отдаёт состояние и замеры:
  программно нажимает кнопки (через тот же код опроса, что и физические), крутит энкодер, читает
  буфер экрана, гистограммы опоздания тактов и длительность долгих операций.
- **Два независимых измерителя тайминга:** интервалы байтов Clock на ПК (то, что «слышит» ведомый
  инструмент, точность ~1 мс вместе с джиттером USB-MIDI и Windows) и часы самого ESP32 (опоздание
  такта относительно расписания, точность до микросекунды).

Принцип тестов: **тест описывает правильное поведение; провал = дефект подтверждён.** Тесты, где
расхождение может быть замыслом автора, помечаются `@pytest.mark.design` — их результат формулируется
как вопрос автору, а не как ошибка.

## Обвязка прошивки

Тестовая сборка — отдельное окружение PlatformIO; в обычной сборке ничего из обвязки не компилируется.
В ESPidi это выглядело так:

```ini
[env:test]
build_flags = -DARDUINO_USB_MODE=1 -DARDUINO_USB_CDC_ON_BOOT=1     ; USB-консоль через HWCDC
build_src_flags = -DESPIDI_TEST -include test_hooks.h            ; макрос и заголовок — только в коде проекта
```

Для RED SEA лучше держать обвязку отдельно от кода автора (например, каталог `testfw/`, добавленный в
`build_src_filter` только окружения `test`), а в `REDSEA.ino` — лишь короткие вставки под
`#ifdef REDSEA_TEST`. Макрос назвать по-своему.

### Что из `reference/espidi_firmware/test_hooks.*` переносится как есть

- **Протокол консоли.** Строка `<id> <команда> [аргументы]\n` → ответ `@<id> {json}\n`. Ответы копятся
  и уходят в USB одним блоком после выполнения команды (`Serial.flush()` обязателен — HWCDC держит
  неполный 64-байтный пакет).
- **Виртуальные кнопки.** `#define digitalRead(p) th_digitalRead(p)` через `-include`: пока включён
  режим `virt 1`, для пинов кнопок возвращается заданный уровень. Код опроса кнопок и энкодера
  прошивки работает без изменений, включая антидребезг и долгие нажатия.
- **Команды, не зависящие от прошивки:** `ping` (версия сборки, причина сброса), `stats [reset]`,
  `events`, `virt`, `press`/`release`, `enc <n>`, `screen` (буфер SSD1306 в hex), `rxlog [clear]`
  (сырые байты MIDI-входа с метками времени), `txflood <сек>`, `reboot`.
- **Метрики:** гистограммы длительности цикла (`th_loopBegin`), зазоров обслуживания (`th_serviceMark`),
  опоздания внутреннего такта (`th_tickLate`), длительность именованных участков (`TH_SCOPE("имя")`),
  счётчик записей во флеш (`th_countCommit`), журнал входящих байтов (`th_logRx`). Метрики пишут
  несколько задач — изменения под критической секцией.

### Что писать заново

- Команды состояния и управления: в ESPidi это `state`, `app`, `param` (меняет параметр через тот же путь,
  что энкодер), `load`, `seqdump`, `eeprom`, `fs`. В RED SEA — свои: страница, движок погоды, параметры
  `state.params[]`, шаги секвенсора, режимы BYPASS/FREEZE, сброс к умолчаниям.
- Точки вставки метрик в `REDSEA.ino`, ориентировочно: начало `loop()`; `generateInternalTicks()` —
  опоздание такта относительно `lastInternalTickMicros`; `processExternalClockTick()`; `updateDisplay()` и
  каждый `display.display()`; запись настроек (`storage.begin/put*/end`, `saveSequencerSettings()`);
  `sendCC`/`sendNoteOn`/`sendNoteOff`; чтение `midi.read()` в `processMIDI()` для `rxlog`.
- В RED SEA глобальный UART называется `midi` (`HardwareSerial midi(1)`), MIDI-библиотеки нет.

## Методика, которая себя оправдала

- **`SteppedClock` для логики.** ПК шлёт один Clock, ждёт, пока устройство «договорит», затем следующий.
  Каждое событие привязано к номеру такта — джиттер ПК на результат не влияет. Параметр `max_wait`
  держать меньше любого тайм-аута «Clock пропал» в прошивке (в ESPidi остановка через 0,5 с → 0,35 с).
- **Контрольный простой (`B1`) перед тестами тайминга.** Если в простое интервалы шумят — стенду
  нельзя верить, а не прошивке.
- **Замеры «до/после» на одном стенде** — каждая правка подтверждается цифрами. Сырые выгрузки тестов
  сохраняются в `results/<время>/results.json`; из них строятся отчёты.
- **Снимок экрана по буферу** проверяет содержимое, но не вид: изменения раскладки интерфейса
  проверять и глазами (в ESPidi тест не заметил, что строка SAVE уехала за край трёхстрочного экрана).
- После теста, отправляющего SysEx, перезагружать устройство (кабель обрезает SysEx, см. ниже).

## Подводные камни (Windows 11, ПК пользователя)

**MIDI на стороне ПК**
- **Ableton Live** захватывает порты `USB2.0-MIDI`; при его зависании замирает служба Windows MIDI
  (`midisrv`), и зависает даже перечисление портов. python-rtmidi держит GIL, поэтому тайм-аут внутри
  процесса не спасает — стенд проверяет порты в подпроцессе. Лечение: закрыть Ableton, перезапустить
  службу (`Restart-Service midisrv -Force`, нужны права администратора — у агента их нет, просить
  пользователя), переподключить кабель.
- **После переподключения USB-MIDI** Windows может показать порт дважды (старый и новый индекс), и ни
  один не открывается («error creating Windows MM MIDI port»). Лечение — перезапуск `midisrv`.
- **USB-MIDI кабель обрезает любой SysEx длиннее 3 байт** до первого USB-пакета (`F0 7D 01`, F7 теряется).
  Поведение с SysEx этим кабелем оценивать нельзя — только `F0 xx F7`.
- **MIDI OUT молчит при живом входе** — почти всегда железо: перемычки Type B, переходники, кабель.
  См. `docs/device/DEVICE.md`.

**USB-консоль (HWCDC)**
- Первый обмен после сброса или простоя теряется → `Console.handshake()` с повторами.
- Без `Serial.flush()` короткие ответы застревают в FIFO.
- Длинные строки (`fs put`) переполняют приём → `Serial.setRxBufferSize(2048)`.
- `Serial.setTxTimeoutMs(30)` — чтобы прошивка не подвисала, если порт никто не читает.
- При перезагрузке устройства pyserial на Windows иногда падает с access violation во время
  переподключения USB → сначала переоткрывать тот же порт по имени, не перечислять все.
- Осиротевший процесс pytest/python держит COM-порт (`PermissionError: Access is denied`) → найти и
  завершить его.

**Сборка и прошивка**
- `pio` — `%USERPROFILE%\.platformio\penv\Scripts\pio.exe`. Первая сборка нового проекта компилирует
  фреймворк (~1 мин).
- **Не направлять вывод `pio run -v` в `head`/`grep … | head`**: после закрытия канала PlatformIO на
  Windows зависает. Писать вывод в файл и смотреть его.
- Перепрошивка не стирает NVS — настройки прошлой прошивки остаются. При переключении между ESPidi и
  RED SEA — `pio run -t erase` перед заливкой.
- Если для проверки на устройство заливалась обычная (не тестовая) сборка, после проверки вернуть
  тестовую.
- Длинные Python-скрипты не передавать через heredoc в bash — сохранять во временный файл и запускать.

## Снимки экрана для документации

- `oled/render_screens.py` — рисует буфер SSD1306 как настоящий OLED (белые пиксели, сетка, свечение).
  Вход — `screens/raw.json` вида «имя кадра → 512 байт буфера в hex». От прошивки не зависит.
- `reference/espidi_capture_screens.py` — как в ESPidi снимались кадры: прошивка приводится в нужное
  состояние через консоль, и команда `screen` отдаёт буфер. Для RED SEA — образец.
