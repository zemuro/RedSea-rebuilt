# Ревью прошивки RED SEA

Код: `REDSEA.ino`, коммит автора `a424db2`. Ревью сделано чтением кода, до замеров на устройстве.

Находки разделены на три группы:

- **Д — дефекты, видимые из кода.** Поведение расходится с очевидным замыслом или с MANUAL.md, и это
  следует из текста программы без допущений. Тест на устройстве нужен, чтобы показать дефект в цифрах
  и потом подтвердить исправление.
- **Г — гипотезы.** Вероятная проблема, но её величину (или само наличие) решает только замер.
- **В — вопросы автору.** Поведение может быть задумано; решает Даниил.

Номера строк — по `a424db2`.

**Откуда опоздания.** Полный кадр по I²C — 12,7 мс; отрисовка страницы MAIN — ещё 6–10 мс; кадр
повторяется каждые 50 мс, даже если ничего не изменилось. Пока кадр рисуется и передаётся, ни
внутренний такт, ни входящий `0xF8` не обрабатываются. Интервалы между тактами на 120 BPM вместо
ровных 20,8 мс выглядят так: 37,1 / 4,6 / 20,9 / 24,5 / 17,1 / 32,9 / 8,8 мс. Кадр анимации перехода
BYPASS/FREEZE дороже всего: у ESP32-C3 нет аппаратной плавающей точки, а `sqrt` и `map` считаются для
каждого из 4096 пикселей.

**Позже найдено: кадр дорожает со временем работы (Г7).** Аргументы `sin`/`cos` в анимациях растут
вместе с временем анимации; когда аргумент больше ~200, `sinf` из newlib переходит на точное, но
очень медленное приведение к периоду. Через ~3 минуты после включения отрисовка MAIN дорожает с ~6 до
~32 мс, кадр с передачей — до 48–54 мс при периоде перерисовки 50 мс. Экран рисуется на каждом проходе,
внутренний такт выдаётся по одному за проход, и **темп проседает: −25 % на 120 BPM, −66 % на 240 BPM**;
вход MIDI при внешнем Clock ждёт до 57 мс. Первые замеры выше сделаны в первые минуты после
перезагрузки и этого не показали; тесты тайминга теперь идут и «сразу после включения», и «через
10 минут» (время анимации выставляет обвязка).

**Что не нашлось.** Темп внутреннего Clock не уходит (отставание догоняется), NVS не изнашивается
повторной записью одинаковых данных.

## Как устроен цикл

Всё выполняется в одном `loop()` по порядку:

1. `processMIDI()` — до 64 входящих байтов; на каждый `0xF8` сразу вызывается `onClockTick()`.
2. Кнопки, энкодер, долгие нажатия.
3. Раз в 50 мс экран помечается «грязным» — анимации идут всегда, даже без изменений.
4. `updateDisplay()` — полная отрисовка кадра и передача его по I²C (`display.display()` внутри
   каждой `draw*()`).
5. Внутренний Clock: `generateInternalTicks()` выдаёт **не больше одного такта за проход**, и только
   после отрисовки.
6. Сохранение настроек: раз в 2 с по флагам и раз в 5 с — секвенсор без всяких условий.

MIDI Clock наружу не отправляется ни во внутреннем, ни во внешнем режиме: устройство — только
ведомое (или самостоятельное), но не ведущее.

## Д — дефекты, видимые из кода

### Д1. BPM больше 255 не помещается в переменную
`sequencerBPM` объявлен как `uint8_t` (стр. 188), а диапазон в коде — 1…300: энкодер
(`clampInt(v, 1, 300)`, стр. 1537), случайный выбор (`random(1, 301)`, стр. 1776), проверка при загрузке
(стр. 3221), `putUChar` при сохранении.
**Следствие.** Энкодер от 255 вперёд даёт 256 → 0: на экране «0», темп падает до запасных 120
(стр. 925). Дальше 1, 2, 3… — темп становится очень медленным. Рандомизация подстраницы setup с
вероятностью ~15 % ставит темп 256–300, то есть фактически 0–44 BPM.
**Исправление.** Тип `uint16_t`, сохранять `putUShort`. Решить с автором, нужен ли верхний предел 300
(тогда — с учётом Г1) или достаточно 255.

### Д2. Номера CC сохраняются только для параметра под курсором
Флаг `needSaveCC` один на все четыре параметра, а запись (стр. 3398–3403) сохраняет только
`cc[selectedParam]` — номер того параметра, на котором курсор **в момент записи**.
**Следствие.**
- Рандомизация CC (PLAY+TAP на странице CC) меняет все четыре номера, но после перезагрузки
  вернутся три старых.
- Сброс страницы CC к умолчаниям (удержание ENC_SW 3 с) — то же самое.
- MIDI Learn: если за 2 с до записи курсор ушёл на другой параметр, выученный номер не сохранится,
  а сохранится номер соседа (который и так не менялся).

MANUAL обещает: «Power off mid-edit and nothing is lost».
**Исправление.** Сохранять все четыре номера (четыре `putUChar`, NVS не перезаписывает одинаковые
значения — это проверим замером, см. Г4).

### Д3. После Stop → Start движки RAIN и SNOW «зависают» на время прошлого прогона
Внешний Start (`0xFA`, стр. 1142) обнуляет счётчик тактов `midiTicks`, но не трогает запланированные
на абсолютные номера тактов события:
- `rainNextTick[]` — RAIN мутирует параметр, только когда `midiTicks` дорастёт до старого значения.
  Если до Stop играли 5 минут, после Start RAIN молчит до 5 минут.
- `snowFreezeUntilTick[]` — заморозка, наложенная SNOW, держится, пока счётчик не догонит старый номер.
- `sunReflectNextTick[]` — серия RFLCT, взведённая до Stop, сработает с большой задержкой.

`resetSequencerState()` их тоже не сбрасывает. При внутреннем Clock счётчик не обнуляется, поэтому
дефект проявляется только с внешним Clock — то есть в типичной работе от DAW или драм-машины.
**Исправление.** При Start сбрасывать эти расписания (или пересчитывать относительно нового нуля).

### Д4. Первый шаг после Start пропускается
`resetSequencerState()` ставит `sequencerPlayhead = 0`, а в `onClockTick()` плейхед **сначала
увеличивается**, потом шаг играет (стр. 965–987). Первым звучит шаг 2 (индекс 1), и не на первом такте
после Start, а через 6 тактов (1/16). Шаг 1 впервые звучит только через такт (16 шагов).
С внешним Clock: Start → первый `0xF8` → тишина на сильной доле. При запуске двойным TAP — то же самое
(стр. 1257–1260).
**Исправление.** Первый шаг играть на первом такте после Start (типичная схема: шаг на такте 0, затем
каждые `ticksPerStep`).

### Д5. Время анимации ломается после второго выхода из FREEZE
При входе во FREEZE запоминается `frozenAnimTime`, но `animationPauseTime` не присваивается нигде
(объявлен на стр. 248, остаётся 0). При выходе (стр. 3293) к смещению прибавляется `millis() - 0`,
то есть всё время работы устройства.
**Следствие.** После первого выхода из FREEZE время анимации начинается заново с нуля (анимация
дёргается, а не продолжается с места паузы). После второго выхода смещение становится больше
`millis()`, время анимации — «отрицательным», то есть около 4,29·10⁹. У `float` при таких значениях шаг
около 512 мс, поэтому всё, что анимируется через `sin(time/…)` (линии моря, кораблик, снег, туман),
начинает двигаться рывками раз в полсекунды. Это дефект графики, но замысел ясен — пауза анимации на
время FREEZE.
**Исправление.** Одна строка: `state.animationPauseTime = millis();` при входе в паузу.

### Д6. Сохранение секвенсора каждые 5 секунд без проверки изменений
`saveSequencerSettings()` (стр. 3437–3441) раз в 5 с открывает NVS и пишет 4 значения и блоб шагов
(16 × 8 байт), в том числе во время игры. Если NVS не сравнивает новые данные со старыми, это постоянная
запись во флеш (износ) и остановка процессора на время записи. Если сравнивает — остаётся только
чтение и сравнение, но всё равно в пути тактов. Размер эффекта — см. Г4.
**Исправление.** Флаг изменений, как у остальных настроек; запись не во время игры (по Stop или
в паузе).

### Д7. Энкодер теряет щелчки, когда цикл занят
`handleEncoder()` (стр. 1497–1501) за проход учитывает **один** щелчок (4 перехода), а остаток
обнуляет. Если за время отрисовки кадра (десятки миллисекунд) накопилось 8 или 12 переходов, лишние
пропадают — при быстром вращении значения меняются медленнее, чем крутится ручка. Вдобавок
`encoderTicks = 0` не защищён от прерывания: переход, пришедший между чтением и обнулением, теряется.
**Исправление.** Забирать накопленные щелчки целиком (`mov = ticks / 4`, остаток оставлять),
чтение-обнуление — под запретом прерываний.

### Д8. Мелочи
- `mutateParam()`: проверка `state.frozen[idx] || idx >= NUM_PARAMS` читает массив до проверки
  индекса (стр. 542). Сейчас вызывается только с верными индексами — порядок поменять.
- MIDI Learn для CC секвенсора не ставит флаг сохранения — сохраняется только благодаря Д6.
- Значения по умолчанию расходятся: `sunDflct` — 0 в `State` и при сбросе, 64 при первой загрузке
  (стр. 1877, 3186); `sequencerCC` — 0 в `State` и при сбросе, 20 при загрузке (стр. 3222).
- `retrigIndex`, `wavesIndex` из NVS не проверяются при загрузке; `retrigNames[retrigVal]`
  (стр. 2927) выйдет за массив, если блоб испорчен. Блоб пишет только эта же прошивка, риск низкий.

## Г — гипотезы для замера

### Г1. Внутренний Clock опаздывает на время кадра и проседает на быстрых темпах
Такт проверяется один раз за проход, после `updateDisplay()`, и выдаётся не больше одного за проход.
Кадр перерисовывается каждые 50 мс; передача полного кадра SSD1306 по I²C на 400 кГц — около 12–14 мс,
плюс отрисовка (шум и дизеринг попиксельно).
**Ожидание.** Такты, выпадающие на проход с кадром, опаздывают на 15–25 мс. Пока проход короче
периода такта (20,8 мс при 120 BPM), опоздание догоняется за счёт `lastInternalTickMicros += period`
(уход темпа нет, есть джиттер). Когда кадр дольше периода (≥ ~150 BPM при кадре 16 мс), догнать не
получается: каждый проход с кадром даёт ровно один такт, темп проседает. Во время анимации перехода
BYPASS/FREEZE (150 мс, `sqrt` на каждый из 4096 пикселей, кадр на каждом проходе) — ещё хуже.
**Как мерить.** Снаружи без изменения прошивки: FOG + ARM + AMT > 0 отправляет CC на каждом такте,
то есть интервалы CC на ПК — это интервалы тактов. Изнутри — гистограмма опоздания такта в
тестовой сборке.

### Г2. Реакция на внешний Clock зависит от отрисовки
`0xF8` обрабатывается в `processMIDI()` в начале прохода. Если байт пришёл во время отрисовки, ответ
(CC, нота) уходит после её окончания.
**Ожидание.** Задержка ответа на такт от <1 мс до ~15–25 мс, неравномерная — в такт музыки это
слышно как «плывущая» модуляция и ноты.
**Как мерить.** ПК шлёт Clock, FOG отвечает CC на каждый такт: задержка «Clock → CC» по меткам ПК.

### Г3. Внешний Clock без Start + запуск секвенсора двойным TAP = двойная скорость
`midiRunning` выставляется только по Start/Continue. Многие DAW шлют `0xF8` постоянно, в том числе
в стопе, без Start. Тогда `midiRunning == false`, каждый `0xF8` вызывает `onClockTick()`, а если
секвенсор запущен двойным TAP, `loop()` ещё и генерирует внутренние такты (стр. 3377). Обе
последовательности увеличивают общий `midiTicks` — темп примерно складывается.
**Как мерить.** ПК шлёт Clock 120 BPM без Start; двойной TAP; считаем ноты секвенсора за 10 с.

### Г4. Запись в NVS: пишет ли одинаковые данные и сколько стоит
Замерить длительность `saveSequencerSettings()` и блока записи по флагам, число реальных записей во
флеш при неизменных данных, и опоздание тактов в момент записи.

### Г5. Пропускная способность MIDI-выхода
FOG отправляет 4 CC на каждом такте, даже если значения не изменились (12 байт ≈ 3,8 мс на проводе).
Плюс шаг секвенсора, ретриггер 1/64 (каждый такт), арпеджио RFLCT. На 120 BPM это около 20 % полосы,
на 255 BPM — около 40 %. Буфер UART при этом не переполнится, но `midi.write()` может блокировать
цикл, если аппаратный FIFO (128 байт) заполнен. Замерить максимальную длительность отправки
в тяжёлых сочетаниях.

### Г6. Направление энкодера
`ENC_A = 5`, `ENC_B = 6` — наоборот относительно ESPidi. Проверить на устройстве, что «по часовой» =
увеличение.

## В — вопросы автору

1. **Ноты секвенсора не выключаются.** Шаг отправляет только Note On (стр. 873); Note Off уходит лишь
   перед ретриггером той же ноты. Stop, смена канала, BYPASS не гасят звучащие ноты. Для ударных и
   однократных сэмплов это нормально, для синтезатора ноты будут висеть. Задумано ли так? Если нет —
   какая длина ноты нужна (фиксированная, до следующего шага, параметр)?
2. **Clock наружу.** При внутреннем темпе устройство не отправляет `0xF8`/Start/Stop, поэтому
   подключённые инструменты не синхронизируются с ним. Это осознанно (README: «sits between a MIDI
   clock source and connected gear»)?
3. **MIDI Thru.** Входящие ноты, CC и Clock не проходят на выход. Задумано?
4. **FOG: случайный CC перед LFO.** В FOG на границе интервала WAV сначала срабатывает `mutateParam()`
   (случайный сдвиг, отправляет CC), а затем на том же такте LFO перезаписывает значение и отправляет
   ещё один CC. Получается короткий случайный выброс перед значением LFO. Задумано ли это как
   «шероховатость» FOG или это остаток кода?
5. **LFO отправляет CC на каждом такте**, даже если значение не изменилось. Отправлять только
   изменения?
6. **Шаг секвенсора, запущенного двойным TAP при внешнем Clock**, отсчитывается от момента нажатия, а
   не от доли. Нужна ли привязка к сетке (запуск с ближайшей доли или такта)?
7. **MIDI Learn отменяется** кнопками PAGE и ENC_SW, но не TAP и не PLAY, а MANUAL говорит «Any button
   press cancels the wait». Поправить код или текст?
8. **Внешний Clock в стопе.** Если DAW шлёт Clock без Start, движки (FOG/SUN/RAIN/SNOW) модулируют
   по нему, секвенсор стоит. Так и задумано?
9. **Верхний предел BPM** — 300 или 255 (см. Д1)?
10. **Разбиение на файлы** — пользователь спросит автора отдельно; работаем на монолите.

### Note Off: спецификация (ответы автора)

1. Нота звучит до следующей активной ноты, в том числе через пустые шаги; единственная нота в
   паттерне звучит весь круг.
2. Смена ноты: сначала Note Off старой, потом Note On новой (без перекрытия).
3. Та же нота на следующем активном шаге — перезапуск (Off и сразу On).
4. Ретриггеры — как сейчас (Off+On той же ноты, «перетекание» на пустые шаги с RTRG ≠ 0); после
   последнего ретриггера нота звучит до следующей активной ноты.
5. Принудительно гасить: Stop (кнопкой и внешним `0xFC`), смена MIDI-канала (Off на старом канале),
   вход в BYPASS (Off до того, как выход заглушится). По Stop дополнительно All Notes Off (CC 123).
   FREEZE — по обычным правилам (шаг под курсором перезапускает ноту).
6. Арпеджио RFLCT (SUN) — как сейчас, независимо от секвенсора.
7. Нота, изменённая энкодером во время звучания, не меняется до следующего прохода шага; Note Off
   уходит звучащей ноте.

## Волна «экран» (сделано на ветке `rebuilt`)

Три правки, каждая отдельным коммитом; картинка проверялась по эталонным кадрам
(`tools/scripts/frames.py`: 210 сценариев, 1708 кадров с фиксированным временем и зерном `random()`).

1. **Отрисовка** — неизменные вычисления вынесены из попиксельных циклов: переход BYPASS/FREEZE без
   `sqrt` (d² < r²), пороги дизеринга и линий моря считаются один раз. Совпадает побитно.
2. **Передача по I²C в отдельной задаче.** Драйвер I²C ждёт шину без нагрузки на процессор (92 %
   времени свободно), поэтому `display.flush()` только копирует кадр, а задача с приоритетом выше
   `loop()` отправляет его. Кадр, не изменившийся с прошлой отправки, не передаётся. Совпадает побитно.
3. **`animSin`/`animCos`** — большой аргумент приводится к периоду через `fmod`. В первые минуты и
   «через 10 минут» совпадает побитно; «через 10 часов» 4 кадра из 1708 (снег) отличаются сдвигом
   снежинки на пиксель. Это единственная правка, где картинка не побитно та же, — отметить автору.

| то же через 10 минут | 48 мс | 6,6 мс |

## Износ флеша NVS (замер 2026-10-04)

`nvs_get_stats()` считает удалённые записи свободными и перезапись не показывает, поэтому замер —
по физическому состоянию страниц NVS прямо с флеша (команда обвязки `nvsraw`: битовая карта состояний
записей и порядковые номера страниц). Одна запись NVS — 32 байта; раздел — 5 секторов по 4 КБ,
630 записей.

| Режим (1 минута) | Физических записей | Стираний сектора | Одно сохранение |
|---|---|---|---|
| простой (сохранение секвенсора вызывается каждые 5 с) | **0** | 0 | ~1 мс — только чтение и сравнение |
| правка ноты шага каждые 0,5 с | 78 | 0 | до 3,7 мс (однажды 20 мс) |
| правка GLIDE каждые 0,5 с | 49 | 0 | до 3,7 мс |
| правка номера CC каждые 0,5 с | 33 | 0 | до 2,8 мс |

NVS (библиотека ESP-IDF, не контроллер флеша) сравнивает новое значение со старым и одинаковое не пишет;
изменённое дописывает на новое место, сектора стираются по кругу. Ресурс: ~100 000 стираний на сектор ×
5 секторов × 126 записей ≈ 60 млн записей. Худший измеренный режим (непрерывная правка шагов,
78 записей в минуту) — около 1,5 лет правки без перерыва; час правки в день — десятки лет. Износ — не
проблема; проблема — тайминг: каждое реальное сохранение останавливает процессор на 3–20 мс (волна 2).
