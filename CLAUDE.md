# RedSea-rebuilt — ревью, отладка и оптимизация прошивки RED SEA

## Что это
**RED SEA** — алгоритмический CC-модулятор и 16-шаговый секвенсор для железа ESPidi (ESP32-C3).
Четыре «погодных» движка (FOG, SUN, RAIN, SNOW), режимы BYPASS/FREEZE, MIDI Learn, анимированная графика.
Автор — **Даниил Власенко**; репозиторий github.com/Cirocular-Vlasenko-Daniil/Red-Sea, лицензия MIT
(код), документация — CC BY 4.0. Код — один файл `REDSEA.ino` (~3400 строк), комментарии на русском.

**Код — Даниила.** Предлагаем правки, не переписываем логику без согласования. Всё, что меняет
поведение или замысел (в том числе графику и анимации — это часть идеи прошивки), — сначала вопрос
автору. Явные ошибки чиним, но тоже отдельными понятными коммитами.

Проект повторяет подход ESPidi-rebuilt (github.com/zemuro/ESPidi-rebuilt): там прошивка ESPidi того же
железа была проверена автотестами на устройстве, исправлена волнами и отправлена автору PR-ами.

## Сборка
- Каноническая сборка — PlatformIO (`platformio.ini` в корне; код автора собирается из корня,
  каталоги `tools/` и `docs/` исключены фильтром). `pio` = `%USERPROFILE%\.platformio\penv\Scripts\pio.exe`.
- **Точка отсчёта достигнута:** код автора (коммит `a424db2`) собирается без изменений —
  флеш 26,5 % (346 860 байт), ОЗУ 4,8 %. Пока исходник не изменён, `pio run` — это сборка автора.
- Тестового окружения `test` ещё нет — появится вместе с обвязкой (см. `tools/RIG.md`).

## Устройство и стенд
- Железо, выводы, MIDI, экран, флеш, устройство пользователя — `docs/device/DEVICE.md`.
- Стенд, что переносится из ESPidi и что писать заново, методика, подводные камни — `tools/RIG.md`.
- Устройство пользователя одно; на нём бывает то ESPidi, то RED SEA. При переключении прошивок
  **стирать флеш** (`pio run -t erase`): NVS и LittleFS переживают перепрошивку.
- Устройство: COM5. MIDI ПК: `USB2.0-MIDI`. Если MIDI-порты не открываются или видны дважды —
  просить пользователя перезапустить службу `midisrv` от администратора.

## Порядок работ
1. ✅ Снимок кода автора (ветка `main` = `upstream/main`, `a424db2`).
2. ✅ Чистая сборка без изменений = точка отсчёта.
3. Ревью кода: архитектура цикла, тайминг Clock (внутренний и внешний), MIDI-вход/выход, запись в NVS,
   экран, кнопки и энкодер. Список гипотез — ниже.
4. Тестовая обвязка прошивки (окружение `test`, вставки только под `#ifdef`) и тесты в `tools/tests/`.
   Обычная сборка должна остаться побайтно сборкой автора по поведению.
5. Прогон на устройстве → отчёт: подтверждённые дефекты с цифрами + вопросы автору по поведению.
6. Исправления волнами, каждая — отдельные коммиты по областям и PR автору с замерами «до/после».
7. Документация и выпуск (по примеру ESPidi-rebuilt: мануал, отчёт, архив с прошивкой).

## Первые наблюдения по коду (гипотезы, не проверены)
- Всё в одном `loop()`: MIDI, кнопки, энкодер, отрисовка, внутренний Clock, сохранение.
  Внутренний такт проверяется **один раз за проход и после `updateDisplay()`**; `generateInternalTicks()`
  выдаёт не больше одного такта за проход. Экран перерисовывается целиком каждые 50 мс (анимации) —
  такты, вероятно, опаздывают на время отрисовки и передачи кадра (полный кадр ≈ 14 мс по I²C).
- Анимация перехода BYPASS/FREEZE считает `sqrt` и `map` для каждого из 4096 пикселей за кадр.
- `saveSequencerSettings()` вызывается каждые 5 с без проверки изменений, в том числе во время игры
  (запись во флеш останавливает процессор). Нужно замерить, пишет ли NVS одинаковые данные заново.
- Внешний Clock обрабатывается в том же цикле → задержка реакции на `0xF8` зависит от отрисовки.
- Свой MIDI-парсер с running status; используются только CC (MIDI Learn) и транспорт. Входящие ноты
  и прочее на выход не проходят — проверить, так ли задумано.
- `ENC_A = 5`, `ENC_B = 6` — наоборот относительно ESPidi; проверить направление на устройстве.
- README ссылается на `LICENSE-DOCS`, которого в репозитории нет.

## Уроки ESPidi, которые стоит помнить
- Тайминг чинится не ускорением отдельных операций, а выносом тактов в задачу FreeRTOS с высоким
  приоритетом и точным таймером (`reference/espidi_firmware/engine.*`), плюс очередь отправки MIDI с
  приоритетом Clock (`midi_serial.*`). Кадр рисовать под блокировкой, отправлять по I²C — вне её.
- Долгие операции (чтение файлов, запись во флеш) убирать из пути тактов; запись настроек — по STOP.
- Изменения раскладки экрана проверять снимком экрана *и* глазами пользователя.
- Каждый тест проверять сначала на исходной прошивке: он должен падать там, где дефект есть.
